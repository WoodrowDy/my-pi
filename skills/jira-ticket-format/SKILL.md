# 지라 티켓 서식

아래에 붙여 넣는 내용(회의 메모, 설계 문서, 작업 기록, 대화 내용)을 이 서식의 지라 티켓 본문으로 정리한다. FE, BE, 앱 작업에 같은 틀을 쓴다. 정리한 티켓은 공유해서 댓글을 받는 용도이므로, 읽는 사람이 "어디를 보고 무엇을 하면 되는지" 알 수 있어야 한다.

## 섹션 목록

이름, 아이콘, 순서는 이 목록대로만 쓴다.

| 순서 | 섹션 | 구분 | 담는 것 | 넣는 경우 |
|---|---|---|---|---|
| 1 | 🏷️ 개요 (Overview) | 기본 | 작업 목적, 배경, 관련 문서 | 항상 |
| 2 | ⚙️ 요구사항 (Requirements) | 기본 | 주제별 규칙, 입력·출력, 상태별 동작 표 | 항상 |
| 3 | 📋 시나리오 (Scenario) | 선택 | 정상 / 예외 흐름 | 사용자 흐름이나 분기가 있을 때 |
| 4 | 🔌 변경 내용 (Changes) | 선택 | API 변경, DB 변경, 현재 상황, 영향 범위, 주의 사항 | 인터페이스나 데이터가 바뀔 때 |
| 5 | ✅ 테스트 케이스 (Test) | 기본 | 구분 / 케이스 / 기대 결과 | 항상 |
| 6 | ❓ 결정 사항 (Decisions) | 기본 | 결정됨, 협의 필요, 범위 밖 | 항상 |

## 규칙

1. 선택 섹션은 내용이 있을 때만 넣는다. 넣을 때는 목록 순서의 제자리에 넣는다.
2. 번호는 들어간 섹션에만 순서대로 붙인다. 기본 4개만 쓰면 [1]~[4], 전부 쓰면 [1]~[6]. 다른 섹션을 가리킬 때는 번호가 아니라 이름으로 쓴다 (예: "요구사항 2.3 기준").
3. 요구사항은 주제 단위로 2.1, 2.2처럼 나눈다. 화면 작업이면 주제 이름 뒤에 화면 경로를 괄호로 붙인다. 입력·출력 항목은 해당 주제 안에 쓴다. 상태에 따라 동작이 달라지면 상태 × 동작 표를 만든다.
4. 시나리오는 Given / When / Then으로 쓴다. 제목은 "정상 — 이름", "예외 — 상황" 형태. 예외는 Then만 써도 된다.
5. 변경 내용의 하위 제목은 API 변경, DB 변경, 현재 상황, 영향 범위, 주의 사항 중 내용이 있는 것만 이 순서로 쓴다. API 변경은 Method / Path / 변경 내용 표. 영향 범위는 단계가 있으면 "N단계: 이름" 아래에 변경·영향을 적는다. 단계별 "확인" 항목은 여기 두지 않고 테스트 케이스로 옮긴다.
6. 테스트 케이스 표의 열은 구분 / 케이스 / 기대 결과로 고정. 구분 값은 정상, 예외, 화면 세 가지만 쓴다.
7. 결정 사항의 세 묶음(결정됨 / 협의 필요 / 범위 밖)은 고정. 결정됨에는 날짜를, 협의 필요에는 상대(FE, 기획, 인프라 등)를 괄호로 붙인다. 범위 밖은 한 줄 요약과 별도 티켓 링크를 둔다. 별도 티켓이 아직 없으면 내용을 그대로 두고, 대화에서 분리를 권한다.
8. 새 종류의 섹션이 필요하면 즉석에서 만들지 말고, 이름·아이콘·순서상 위치를 사용자와 정해 이 목록에 먼저 등록한다. 등록 후보: 🖼️ 화면 (Screens, 요구사항 뒤), 🚀 배포 (Release, 테스트 케이스 뒤).

## 문체

- 개요, 요구사항, 시나리오의 문장은 "~합니다".
- 표의 칸, 변경 내용, 결정 사항의 항목은 명사형 ("~변경", "~유지", "~없음").
- 사용자가 직접 쓴 것처럼 담백하게 쓴다. 원문의 용어와 숫자는 바꾸지 않는다.

## 출력 형식

- 티켓 본문 전체를 코드 블록 하나에 담아 그대로 복사해 붙일 수 있게 준다.
- 목록은 "* " 기호를 쓰고, 한 단계 들어갈 때마다 공백 3칸.
- 표는 마크다운 표. 표는 목록 안에 넣지 않고 소제목 바로 아래에 둔다.
- 섹션 제목 줄은 "아이콘 [번호] 이름 (영문)" 형태. 예: ⚙️ [2] 요구사항 (Requirements)

## 정리할 때 지킬 것

- 받은 내용에 없는 사실을 지어내지 않는다. 처리상태 목록, 오류 코드, 일정, 담당처럼 원문에 없는 값은 비워 두고 대화에서 묻는다.
- 티켓 본문에는 작업 메모나 편집 주석을 남기지 않는다 ("[확인 필요]", "추정" 같은 표시 금지). 판단 근거, 원문에서 엇갈리는 곳, 확인이 필요한 사항은 코드 블록 밖 대화에서 말한다.
- 원문 안에서 서로 다른 값이나 규칙이 보이면 임의로 하나를 고르지 말고 대화에서 짚는다.
- 이전 본이 있으면 무엇이 추가·변경·삭제됐는지 대화에서 요약한다.

## 댓글 반영

공유 후 댓글로 정해진 내용을 받으면:

1. 본문의 해당 규칙을 고친다.
2. 결정 사항의 "결정됨"에 날짜와 함께 한 줄을 추가한다.
3. 해결된 "협의 필요" 항목은 지운다.
